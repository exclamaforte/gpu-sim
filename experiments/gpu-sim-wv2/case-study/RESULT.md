## The anomaly is resolved: it was contention

The published 159.8 ms for d=512 TP2+DP2 does not reproduce. Interleaved median
is 25.8 ms with IQR box [22.4, 29.0], disjoint from and far below d=1024 TP2's
[41.7, 83.1] -- the larger model is slower, as compute requires. The 159.8 ms
draw was a contention spike on a box running loadavg ~1000 during the runs, not
a real effect. No unexplained effect remains; there is nothing to promote to a
finding.

The single draws were misleading in every cell, not just the flagged one: the
published d=512 DP4 (19.3) sits at the observed minimum (19.1), the published
d=1024 TP2 (91.5) sits above the observed maximum (89.0). One draw per cell on
a shared box is not a measurement.

## What the harness says (corrected)

At d_model=1024 the recommendation survives and is now quantified: TP2+DP2
median 56.7 ms vs DP4 median 129.9 ms, IQR boxes disjoint -- TP wins on step
time and on peak memory (1416 vs 2155 MB), at 14% more collective bytes.

At d_model=512 the published crossover ("DP wins") does NOT survive. Point
estimates favor TP2+DP2 (25.8 vs 41.1 ms) but the IQR boxes overlap
([22.4,29.0] vs [25.3,43.6]): at this size the configs are inside each other's
contention noise and the data cannot separate them. The honest statement is
"too close to call at 512", not "DP wins at 512".

That crossover was the useful output of the original table, so this correction
removes it. What remains is a statement about the SOFTWARE configuration at a
fixed declared fabric, not about a real cluster.

## Caveats that must travel with this table

- `step_ms` is median over 8 interleaved reps (round-shuffled cell order, seed
  702): interleaving is what stops shared-box drift from masquerading as a
  config effect. The distribution is right-skewed by contention (max exceeds
  q3 by more than q3 exceeds the median in every cell), so means are not
  reported. Do not raise `--steps` to average inside a run: that cannot
  separate config effect from drift.
- Every collective duration is SYNTHETIC: declared link parameters, never checked
  against real multi-GPU hardware (gpu-sim-wv2 is blocked on that).
- Peak memory is only comparable within one batching convention.
- Losses are not reported: this is a cost study, and `--dp-mean`/transport were off.
